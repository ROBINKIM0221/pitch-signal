# KBO 사례 연구: 구속 데이터 수집 가능성 (단계 7.1)

작성 2026-10-06. 공개 코드 두 가지를 읽고 정리했다. **이 단계에서는 아무 데이터도 받지 않았다.** 아래 '이용 조건' 때문에 시험 수집은 사용자 결정 뒤에 한다.

## 1. 공개 코드가 쓰는 출처

| 코드 | 출처 | 투구별 구속·구종 | 비고 |
|---|---|---|---|
| geonwoong-lee/KBO_Win_Probability (GitHub) | 네이버 스포츠의 문서화되지 않은 API: `/schedule/games`, `/schedule/games/{gameId}/relay?inning=N`(이닝별 문자중계), `/schedule/games/{gameId}/preview` | **있음**. 문자중계 JSON에 투구마다 `speed`(구속), `stuff`(구종)가 들어 있고 한 경기당 약 560개 이벤트 | 코드 자체 제한 초당 2.5회. 저장소는 "수집한 데이터의 저작권은 네이버와 KBO에 있어 코드만 공개"라고 밝힘 |
| kbodata (PyPI 0.2.3, 2024-07) / Hyeonji-Ryu/kbo-data | KBO 공식 홈페이지를 Selenium(Chrome)으로 읽음 | **없음**. 일정, 스코어보드, 타자·투수 경기 기록까지 | 투수 기록은 경기 단위(이닝·투구 수 등)라 구속이 없음 |

투구별 구속이 있는 공개 경로는 네이버 문자중계 API뿐이다.

## 2. 이용 조건에서 걸리는 점

- 네이버 스포츠 API는 공개 문서가 없는 내부 API다. 이 작업 환경에서는 네이버 도메인(`sports.naver.com`, `api-gw.sports.naver.com`)에 접근할 수 없어 robots.txt와 이용약관을 직접 확인하지 못했다. **사용자가 브라우저로 `https://sports.naver.com/robots.txt`와 네이버 서비스 이용약관의 자동 수집 관련 조항을 확인한 뒤 결정해야 한다.**
- 고교 모듈에서는 KBSA 사이트가 robots.txt로 자동 접근을 막고 있어 자동 수집을 하지 않기로 했다(단계 6). 같은 기준을 적용하면, 네이버가 자동 접근을 막는다면 여기서도 자동 수집은 하지 않는다.
- 공개 저장소의 설명대로 받은 데이터는 네이버·KBO의 것이므로, 어떤 경우에도 원데이터는 저장소에 올리지 않고 집계 결과(등판별 평균 구속 등)만 쓴다.

## 3. 받을 수 있다고 할 때 필요한 요청 수 (추정)

세 투수(치리노스·미치 화이트·후라도): 2025 마지막 선발 10경기 + 2026 말소일까지 등판(각 10~20경기) ≈ 투수당 20~30경기, 합계 약 60~90경기.
경기마다 일정 1회 + 이닝 9~10회 ≈ 11회 → **약 700~1,000회 요청**. 간격 1초면 15~20분이면 끝나는 양이다.

## 4. 대안

1. **수기 입력**: 세 투수의 선발 등판은 합쳐야 60~90경기다. 네이버 경기 기록 화면에서 등판별 평균 구속(또는 최고·평균 구속)을 한 경기에 하나씩 옮겨 적으면 1~2시간 안에 끝난다. 단계 7.3의 구속 EWMA는 등판별 평균 구속만 있으면 돌릴 수 있다(등판 안 흔들림은 MLB 개발셋 값으로 대신하고 그 점을 밝힘).
2. **타임라인만(7.4)**: 구속 없이 '신호 → 말소 → 결정' 날짜와 대체 선수 경과만 정리한다. 실행기획서 1.6절의 줄이는 순서 3번.
3. **자료 요청**: KBO 또는 기록 제공사에 연구 목적 자료를 요청한다. 회신까지 시간이 걸려 공모전 일정에는 맞추기 어렵다.

## 5. 결정할 것

- 네이버 이용 조건을 확인한 결과 자동 수집이 가능하면: 한 경기만 시험 수집(요청 간격 1초 이상) → 구속 값이 중계 화면과 같은지 확인 → 7.2 진행.
- 가능하지 않거나 확인이 어려우면: 대안 1(수기 입력)을 권한다. 세 투수 사례의 가치는 '신호가 언제 울렸는가'이므로 등판별 평균 구속으로 충분하다.
